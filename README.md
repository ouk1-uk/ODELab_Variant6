# Лабораторна робота №7 — варіант 6: розв'язання ОДР

**Тема:** Обробка виключень. Тестування програми.  
**Мова:** C++20. **Збірка:** CMake, Visual Studio, Ninja. **Тести:** Google Test через vcpkg.

> Це самостійна реалізація варіанта 6. За умовою лабораторної №7 бібліотеку треба модернізувати з лабораторної №4, але вихідний код роботи №4 не був наданий. Якщо на четвертій лабораторній використовувалися інші алгоритми, інтегруйте їх у цю структуру, зберігши контракти та перевірки.

## Призначення бібліотеки

`ODETask` розв'язує задачу Коші для ОДР першого порядку:

\[
 y'(x) = f(x,y), \quad y(x_0)=y_0, \quad x\in[x_0,x_{end}].
\]

Реалізовано **метод Ейлера** та **метод Рунге—Кутти четвертого порядку (RK4)**. Функція похідної передається як `std::function<double(double,double)>`; траєкторія зберігається у `std::vector<ODEPoint>`. Останній крок скорочується до правої межі інтервалу. Алгоритми обрані для навчальної реалізації: методичка для варіанта 6 не фіксує конкретного чисельного методу.

## Контракт та інваріанти `ODETask`

- `xStart`, `yInitial`, `xEnd`, `step` — скінченні числа (`std::isfinite`).
- `xStart < xEnd`, `step > 0`, `maxSteps > 0`.
- Різниця `xEnd-xStart` повинна бути скінченною.
- Траєкторія або порожня, або починається у `(xStart, yInitial)`, складається зі скінченних точок зі строго зростаючими `x` та завершується точно на `xEnd`.
- Кількість виконаних кроків не перевищує `maxSteps`; кількість точок — не більше `maxSteps + 1` за умови, що додавання одиниці представиме у `size_t`.
- Зміна параметрів успішно очищує попередню траєкторію. Якщо нові параметри некоректні, старі параметри і траєкторія не змінюються.
- `solve` не змінює параметри. Успішний виклик цілком замінює траєкторію; неуспішний — зберігає попередню.

**Зауваження:** гарантія стосується внутрішнього стану `ODETask`. Зовнішні побічні ефекти користувацької функції `f(x,y)` (наприклад, запис у файл) бібліотека не скасовує.

## Ієрархія власних винятків

```text
std::exception
  └── std::runtime_error
       └── ODEException
            ├── NonFiniteValueException
            ├── InvalidDerivativeException
            └── StepLimitException
```

| Операція / помилка | Тип винятку | Діагностика |
|---|---|---|
| Створення/зміна параметрів: `step <= 0` | `std::invalid_argument` | пояснення про додатний крок |
| Створення/зміна параметрів: `xStart >= xEnd` | `std::invalid_argument` | пояснення про інтервал |
| `NaN`/`Inf` у `xStart`, `yInitial`, `xEnd`, `step` | `NonFiniteValueException` | `parameter()`, `value()` |
| Функція `f(x,y)` повернула `NaN` або `Inf` | `InvalidDerivativeException` | `x()`, `y()`, `value()` |
| Потрібно більше ніж `maxSteps` кроків | `StepLimitException` | `limit()`, `requested()` |
| Нульовий `maxSteps`, порожня функція чи невідомий метод | `std::invalid_argument` | текст повідомлення |
| Непредставима ширина інтервалу, арифметичне переповнення або неможливість просунути `x` | `std::overflow_error` | текст повідомлення |
| Доступ до неіснуючої точки `pointAt(index)` | `std::out_of_range` | індекс перевіряється `vector::at` |
| Функція `f(x,y)` самостійно згенерувала виняток | Початковий тип винятку | бібліотека не приховує помилку |

Власні класи потрібні для предметних помилок з діагностичними полями, стандартні — для загальновідомих порушень передумов, переповнення та індексації. Обробники у `demo/main.cpp` розташовані від спеціалізованих типів до загальних і використовують `const &`.

## Гарантії безпеки

| Метод | Гарантія | Обґрунтування |
|---|---|---|
| Конструктор | інваріанти або виняток | перевіряє параметри, некоректний об'єкт не створюється |
| `setParameters()` | **strong** | спочатку всі перевірки, після них лише нездатні генерувати винятки присвоєння і `clear()` |
| `solve()` | **strong** | обчислює повну траєкторію в локальному векторі, потім `trajectory_.swap(prepared)` |
| `xStart()`, `yInitial()`, `xEnd()`, `step()`, `maxSteps()` | **no-throw** | лише читання скалярів, позначені `noexcept` |
| `trajectory()` | **no-throw** | повернення `const&`, позначений `noexcept` |
| `pointAt()` | стан не змінює | перевірений доступ, може кинути `std::out_of_range` |
| `ScopeLogger::~ScopeLogger()` | **no-throw** | `noexcept`, всі винятки потоку перехоплюються |

Сильна гарантія `solve()` реалізується послідовністю **prepare → validate → commit**: створення локального контейнера, усі обчислення/перевірки/додавання точок, фіксація через `swap()` лише після успіху. При `std::bad_alloc` або винятку в `f` зовнішній стан також зберігається.

## Очікувана послідовність RAII (прогноз перед порівнянням із фактичним результатом)

Функція `levelOne` викликає `levelTwo`, а та — `levelThree`; остання викликає `ODETask::solve`, що генерує `InvalidDerivativeException`. На проміжному рівні виняток діагностується та повторно генерується оператором `throw;`.

```text
[enter] levelOne
[enter] levelTwo
[enter] levelThree
[exit] levelThree
[middle] invalid derivative at x=0.0000000, y=1.0000000; rethrow
[exit] levelTwo
[exit] levelOne
[top] caught InvalidDerivativeException: ODE derivative returned NaN or infinity
```

**Фактичний результат** запуску `ODEDemo` у локальній перевірці має саме цей порядок (див. `verification/local_checks.txt`). Локальні об'єкти знищуються у зворотному порядку, а `throw;` зберігає конкретний тип. `ScopeLogger` є RAII-об'єктом: його деструктор виконується під час розкручування стека.

## Демонстрація некоректного підходу

`AntipatternDemo` окремо генерує `int`, `std::string` і `std::invalid_argument`. `catch(const std::exception&)` **не перехоплює** `int`/`std::string`; `catch(...)` перехоплює будь-який тип, проте втрачає зручний єдиний інтерфейс діагностики `what()`. Для бібліотечного коду рекомендовано стандартні та спеціалізовані власні типи винятків.

## Збірка у Windows — Visual Studio 2022 / новіша

Встановіть компонент **Desktop development with C++** із засобами CMake/Ninja. Встановіть `vcpkg` (або використайте наявний екземпляр) і змінну середовища `VCPKG_ROOT`, яка вказує на його кореневу папку. Наприклад, у PowerShell (змініть шлях на ваш):

```powershell
$env:VCPKG_ROOT = 'C:\vcpkg'
& "$env:VCPKG_ROOT\vcpkg.exe" x-update-baseline --add-initial-baseline
cmake --preset windows-debug
cmake --build out/build/windows-debug
ctest --test-dir out/build/windows-debug --output-on-failure
```

> Команду `vcpkg x-update-baseline --add-initial-baseline` достатньо запустити один раз; вона додасть справжній `builtin-baseline` до `vcpkg.json`, який потрібно включити до Git-репозиторію. Значення baseline не підставлено заздалегідь, оскільки воно залежить від вашого реального реєстру vcpkg.

У Visual Studio оберіть **File → Open → Folder**, вкажіть корінь проєкту, виберіть preset `windows-debug`; після конфігурації цілі `ODEDemo`, `AntipatternDemo`, `ODETests` доступні для запуску. Якщо після зміни `VCPKG_ROOT` preset її не бачить, закрийте й заново відкрийте Visual Studio у середовищі зі встановленою змінною. Для збірки через термінал альтернативно можна передати повний шлях `-DCMAKE_TOOLCHAIN_FILE="C:/vcpkg/scripts/buildsystems/vcpkg.cmake"`.

Для запуску окремого тестового виконуваного файла:

```powershell
.\out\build\windows-debug\ODETests.exe
```

Для локальної збірки **без** Google Test (перевірка бібліотеки та демопрограм):

```powershell
cmake -S . -B out/build/local -DODELAB_BUILD_TESTS=OFF
cmake --build out/build/local
```

## Модульні тести

`tests/ODETests.cpp` містить **29 сценаріїв**: обчислення Ейлера та RK4, включення кінцевої точки, крайні значення, усі обов'язкові помилки, відповідність типів винятків, діагностичні поля, інваріанти, RAII та сильну гарантію для похідної, переповнення, зовнішнього винятку та `setParameters()`.

### Негативний самоконтроль

Для перевірки дієвості тестів у **тимчасову копію** `ODETask.cpp` додано помилковий виклик `trajectory_.clear()` на початку `solve()` — перед завершенням розрахунку. Це руйнує попередню траєкторію при невдачі.

- **До ін'єкції помилки:** 29/29 сценаріїв пройдено локальним тестовим адаптером.
- **З навмисною помилкою:** 26/29 пройдено, 3 перевірки гарантії стану провалено.
- **Після відновлення оригіналу:** 29/29 пройдено.

`verification/negative_selfcheck.txt` містить відповідні журнали. **Важливе розмежування:** ці числа отримано за допомогою локального адаптера макросів Google Test, оскільки в середовищі перевірки пакет Google Test недоступний. Це реальний запуск тих самих перевірок на C++20, **але не офіційний запуск Google Test**. Після встановлення vcpkg необхідно виконати `ctest` та зробити скріншот його результатів для звіту.

## Обмеження

- Реалізовано ОДР першого порядку з одним скалярним станом `y`; системи ОДР і адаптивний крок не входять до цього проєкту.
- Некоректні значення похідної, переповнення та обмеження кроків є помилками бібліотеки; вона не контролює математичну гладкість/збіжність заданої функції `f`.
- Код лабораторної №4 не надано, тому інтеграція з раніше написаною бібліотекою не могла бути перевірена.
- Посилання GitHub та скріншот саме Google Test необхідно додати після фактичного запуску та публікації репозиторію, а не вигадувати.
